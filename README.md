# CompVision — AI-сервис выявления нарушений кассовой дисциплины

Решение кейса ForteBank на Datathon 26. Сервис принимает видеозапись работы кассира (`.mov`, одна камера, без звука), анализирует её локальными моделями и возвращает вердикт — `no_violation` или `violation`. Для каждого найденного события сервис указывает тип нарушения, таймкод, описание того, что видно на видео, кадры-доказательства (JPEG в base64) и ссылку на нормативный источник.

Обработка выполняется полностью локально: облачные AI-сервисы не используются, после загрузки весов интернет не нужен. Результат — подсказка для проверки человеком, а не окончательное заключение.

## Архитектура

Три контейнера, наружу открыт один порт (`FRONTEND_PORT`, по умолчанию `8080`). Backend и worker работают в сети Docker `internal` без выхода в интернет (`internal: true`): маршрута наружу у них нет, поэтому локальность по разделу 7 ТЗ обеспечена технически. Интернет нужен только при сборке образов и для однократного скачивания весов на хосте.

- **frontend** — Vite SPA, раздаётся nginx. nginx проксирует `/api` и `/health` на backend; UI и API живут на одном адресе. Интерфейс ходит на `/ui-api`: nginx переписывает путь в `/api` и сам подставляет `X-API-Key`, поэтому проверяющему ключ не нужен.
- **backend** — FastAPI: создаёт задачу (`POST /api/v1/analyze`), отдаёт статус и результат (`GET /api/v1/jobs/{job_id}`), файлы задачи (`GET /api/v1/jobs/{job_id}/files/{filename}`), настройки интерфейса (`GET /api/v1/config`) и принимает отзыв проверяющего (`POST /api/v1/jobs/{job_id}/feedback`, по умолчанию выключен). Очередь не обслуживает. Все запросы к `/api` защищены заголовком `X-API-Key`.
- **worker** — GPU-контейнер, единственный владелец очереди: по одной забирает задачи из общей SQLite, прогоняет пайплайн на локальных весах из `/models` (только чтение), пишет результат в базу. Задачи, загруженные раньше `JOB_TIMEOUT_SEC` назад и не готовые, переводит в `failed` (отсчёт от загрузки: ожидание в очереди тоже входит в лимит). Нормативные правила читает из `rules.yaml` (`RULES_PATH`).
- **shared/** — общий для backend и worker Python-пакет: схемы ответа (`shared/schemas.py`) и весь SQL очереди (`shared/db.py`, sqlite3 + WAL).

```text
браузер / curl ──:8080──▶ nginx (frontend) ──/api, /ui-api, /health──▶ backend (FastAPI)
                                                                          │
                                                                SQLite + volume (задачи, кадры)
                                                                          │
                                                                    worker (GPU, модели)
```

### Пайплайн анализа

`worker/runner.py`: `analyze` → `process_video` = `scene.build_scene` → `events.detect_events` → `verdict.build_result`.

1. **Восприятие** (`worker/perception`, `worker/scene/pipeline.py`). Кадры извлекаются с частотой 3 к/с. На каждом кадре RT-DETR находит людей и предметы COCO. Собственный трекер (`worker/perception/tracking.py`, IoU + расстояние центров) связывает людей в треки. OWLv2 по 4 ключевым кадрам находит зоны: стол, сейф, дверь, ноутбук. SigLIP раз в секунду оценивает состояния по вырезкам зон (zero-shot, пары позитивных и негативных подписей).
2. **Сцена** (`worker/scene/builder.py`, контракт `worker/scene/contract.py`, пример `docs/scene_contract_example.json`). Из детекций строится временной ряд состояний `SceneTimeline`: сколько людей внутри кассы (люди за стеклом и отражения отсекаются по размеру и положению рамки), на месте ли кассир, вход и выход через дверь, вероятности «сейф открыт», «наличные / сумка / верхняя одежда на столе», «стакан или еда у кассира», «телефон в руке». Кассир — роль, а не личность: трек, который дольше всех и ближе всех находится у рабочего стола. Лица не распознаются.
3. **События** (`worker/events/detectors.py`). Каждое правило из `rules.yaml` вызывает детектор по имени. Детектор строит ряд «вероятность нарушения» p(t) из полей сцены, сглаживает его скользящей медианой (`smooth_points`), выделяет интервалы гистерезисом (начало при p ≥ `p_on`, конец при p < `p_off`), отбрасывает интервалы короче `min_duration_sec` и склеивает ближе `merge_gap_sec`. Таймкод — начало интервала, уверенность — средняя p на интервале. Детекторы R11 и R14 работают по моментам входа посетителя через дверь, а не по гистерезису.
4. **Вердикт** (`worker/verdict`). Остаются события с уверенностью не ниже `min_confidence` своего правила, не больше 5 самых уверенных, в ответе — по времени. Кадры-доказательства (до 3): начало интервала, +1 с и момент максимальной уверенности. Описание строится по шаблону правила и всегда заканчивается ссылкой на пункт акта. `verdict = violation` тогда и только тогда, когда список нарушений не пуст.

**Производительность (измерено).** На RTX 3050 Laptop 6 ГБ восприятие самого длинного ролика датасета (142,5 с) занимает 30 с, пик видеопамяти — 3,7 ГБ. Лимит ТЗ — 5 минут на видео.

#### Поза (экспериментально)

Проход позы выключен по умолчанию: с `ENABLE_POSE=1` worker после сборки сцены ставит 17 точек кассиру и людям из `others` (`worker/perception/pose.py`) и пишет в состояния `cashier_kp`, `others_kp` и признаки `cashier_hand_in_safe`, `cashier_hands_on_desk`, `hand_to_hand` (+ `hand_to_hand_track`), `cashier_counting`, `cashier_hand_at_face`, `cashier_standing` (`worker/scene/pose_features.py`; пороги — в долях ширины плеч человека, не в пикселях). Детекторы по ним — `worker/events/pose_detectors.py`; правила с ними пока только в блоке «ЗАПЛАНИРОВАНО» `rules.yaml`. `POSE_EVERY_K=2` — поза на каждом втором состоянии, если не укладываемся по времени.

- Нужен `transformers >= 4.48` (классы `VitPose*` появились в 4.48.0). Проверка апгрейда 18.10: на CPU `transformers==4.48.3` (+ `tokenizers` 0.21) даёт те же выходы RT-DETR, OWLv2 и SigLIP, что 4.46.3 — RT-DETR на 5 кадрах (61 детекция), OWLv2 на 2 кадрах (72), score и рамки совпали до 4-го знака, косинус эмбеддингов SigLIP 1,000000; в контейнере worker (torch 2.5.1, CUDA, fp16) — тоже без единого расхождения (62 и 72 детекции, вероятности SigLIP), ViTPose там — 10,7 мс на рамку (`data/ml_results/pose/transformers_check.txt`). Образ ставит 4.48.3 отдельным слоем поверх 4.46.3 (`worker/requirements-pose.txt`, `--no-deps`): слой torch не пересобирается. Без новой версии или без весов проход позы пропускается с ошибкой в `meta.pose.error`, анализ не падает. Для замеров без смены основного окружения: `pip install --target <каталог> --no-deps "transformers==4.48.3" "tokenizers>=0.21,<0.22"` и `PYTHONPATH=<каталог>:.`.
- Веса: `python scripts/download_models.py --only vitpose`; проба на трёх кадрах: `scripts/smoke_pose.py`; поза в готовый кэш без перезапуска остальных моделей: `scripts/add_pose_to_cache.py` (`--recompute` — признаки заново по сохранённым точкам, без GPU); контактный лист со скелетами и сработавшими детекторами: `scripts/viz_pose.py`.
- Без распознавания лиц: точки головы — только где находится голова; вырезок и эмбеддингов лиц нет.
- Ограничения: кассир спиной к камере — кисти закрыты корпусом, признаки `null` (это «нет данных», а не «нарушения нет»); ноги под столом — «встал» по высоте рамки; скачки света дают прыгающие точки (медиана по 3 точкам и минимальные длительности); позу считаем только для людей внутри кассы (`others` уже без людей за стеклом).
- Замер 18.10 (поза поверх `data/scene_cache_r3` -> `data/scene_cache_r3_pose`, 42 видео, ViTPose на GPU): точки кассира есть в 92 % состояний (на аугментациях flip / persp / crop / light — 91–93 %), видно в среднем 1,73 запястья из 2; поза занимает медиану 1 с на видео, максимум 5,6 с (Х-39, видео 79 с; самое длинное Х-14, 142 с — 5,1 с).
- Детекторы позы с параметрами по умолчанию (`scripts/eval_pose_detectors.py`; типы нарушений — `training/labels/violation_types.csv`, коды R из таблицы разметки команды): передача из рук в руки ловит X-1 (22 с, пачка возвращается клиенту) и Х-18 (20 с, передача постороннему, R11) и на оригинале, и на аугментациях, но срабатывает и на 5 из 19 чистых видео: передача клиенту — обычная работа. С `min_persons: 3` — 0 из 19 на оригинале (Х-18 остаётся), 1–2 на crop / light / persp. Сейф, пересчёт в одиночку и рука у лица по позе на своих метках не срабатывают и дают до 7 ложных из 19. Правила позы остаются в «ЗАПЛАНИРОВАНО».

##### Головы жестов (гибрид, выключено по умолчанию)

Поверх геометрических признаков — маленькие обучаемые головы жестов (`worker/scene/pose_heads.py`, инференс numpy; обучение — `scripts/train_pose_heads.py`, torch). Учим жесты, а не нарушения: на тип нарушения в датасете чаще всего 1–2 примера (до 6), а жесты есть в десятках видео, в том числе в чистых. Вход головы — точки кассира в окне ±1 с в единицах ширины плеч (без сырых координат кадра, симметрично к отражению), расстояния кистей до стола, сейфа, головы и рук других людей, скорость кистей и сами геометрические признаки.

- Метки — `training/labels/pose_gestures.csv`: 1314 плиток (секунда видео) по 40 видео, по листам `scripts/pose_label_sheet.py` (скелеты, без точек головы); два независимых разметчика, совпадение 88–99 % по жестам, 301 расхождение (3,8 %) решено третьим. «Да»: стоит 253, пересчёт 281, рука в сейфе 101, передача 20, рука у лица 4 (только Х-46).
- Проверка — 5 фолдов по видео, все аугментации видео в фолде оригинала; учим на оригинале и 4 аугментациях (flip, persp, crop, light — поза на каждой посчитана заново). Выбор модели, порога и режима — по вероятностям вне фолда тех же 40 видео (без вложенной проверки): цифры — оценка сверху.
- Включение: `POSE_GESTURE_HEADS=heads/pose_gestures.npz` (вместе с `ENABLE_POSE=1`); веса — `PYTHONPATH=. python scripts/train_pose_heads.py` по меткам из репозитория (каталог `models/` в git не входит). Режим гибрида на жест выбирается по замеру: `head` — вероятность головы вместо геометрии, `geometry` — голова не используется.

| жест | режим | AUC вне фолда, голова / геометрия (оригинал) | F1, голова / геометрия: оригинал | F1, голова: flip / persp / crop / light |
|---|---|---|---|---|
| пересчёт (`cashier_counting`) | head | 0,92 / 0,61 | 0,82 / 0,33 | 0,82 / 0,79 / 0,82 / 0,81 |
| рука в сейфе (`cashier_hand_in_safe`) | head | 0,95 / 0,81 | 0,69 / 0,37 | 0,68 / 0,61 / 0,67 / 0,67 |
| передача (`hand_to_hand`) | head | 0,97 / 0,81 | 0,45 / 0,32 | 0,39 / 0,52 / 0,44 / 0,45 |
| стоит (`cashier_standing`) | geometry | 1,00 / 0,99 | 0,99 / 0,99 | геометрия и так 0,98–0,99 |
| рука у лица (`cashier_hand_at_face`) | geometry | — | — | позитивы только в одном видео: вне фолда не проверить |

Геометрическая «рука в сейфе» срабатывает в 37 % состояний: в 2D кисть у счётной машинки и у ноутбука попадает в зону сейфа (Х-46, Х-14) — голова отличает это по позе. Аугментации в обучении полезны: без них на persp AUC руки в сейфе 0,87 вместо 0,95, F1 пересчёта 0,74 вместо 0,79. Детекторам позы головы пока не помогают: на сценах с головами вне фолда (`train_pose_heads.py --oof-scenes`) передача и пересчёт в одиночку по-прежнему срабатывают на 5–11 из 19 чистых видео — в них кассир так же передаёт деньги клиенту и считает один. Жест распознаётся лучше, но нарушение определяется контекстом (кто второй человек, был ли клиент, порядок действий); для R03 (Х-34: пересчёт после ухода клиента) сцена сейчас видит уход клиента на 4 с позже, чем он происходит.

| [№ 14](https://adilet.zan.kz/rus/docs/V2000020075), подп. 4) п. 16 | ценности передаются через транспортирующее устройство или инкассаторский бункер в передней части кассы | R12 | инкассаторская сумка в кассе при вошедшем человеке |
| [№ 231](https://adilet.zan.kz/rus/docs/V1900019680), п. 12 | личные вещи вне кассового узла; разрешён только перечень (лекарства, медизделия, средства связи без съёмки) | R13 | стакан или еда у кассира |

**Принцип сопоставления.** Каждое правило в `rules.yaml` связывает пункт акта (`source: doc, url, clause`) с детектором (`detector`), который проверяет наблюдаемое состояние сцены, и с шаблоном описания (`template`). Нарушение выводится только по видимому: если для вывода нужны невидимые данные (проводки, сверка, документы, содержание разговора), правило не заводится (раздел 7 ТЗ). Шаблон описывает только то, что видно на кадрах; ссылка на пункт акта добавляется в конец описания и дублируется в поле `rule` ответа.

Правила R11 и R12 опираются на требования Правил № 14 к устройству помещений (изоляция кассы, порядок передачи ценностей), а не на прямой запрет действия. R13 — толкование п. 12 Правил № 231: прямого пункта о еде и напитках на рабочем месте кассира нет ни в одном из актов, но их нет и в перечне разрешённого. Эти три правила — подсказка проверяющему, а не прямой запрет.

Для ноутбука, оставленного без блокировки (ролик Х-28), подходящего пункта в Правилах № 231 и № 14 не найдено, поэтому такой тип не выводится: сервис не ссылается на нормы, которые не сверены с текстом акта.

Файл `rules.yaml` не запекается в образ, а монтируется в worker (`./rules.yaml:/app/rules.yaml:ro`): после правки достаточно `docker compose restart worker`.

## Ограничения и известные ошибки

**Метрики качества** (TP / FN / FP / TN по вердикту, попадание таймкода в ±3 с, время обработки): будет добавлено после прогона `scripts/evaluate.py`.

Принципиальные ограничения:

- Анализ строго визуальный: звук не используется, лица не распознаются (FAQ 29). Намерения, содержание документов, суммы и проводки не оцениваются.
- «Кассир» — роль по положению трека у рабочего стола. Если кассира определить не удалось, правила, которым он нужен, не срабатывают.
- R11, R12 и R13 — подсказки проверяющему, а не прямые запреты: R11 и R12 основаны на требованиях Правил № 14 к устройству помещений, R13 — толкование п. 12 Правил № 231.
- Таймкод — начало интервала нарушения, а не момент «самого нарушающего» действия. Поля `timecode` / `timecode_offset_sec` в `rules.yaml` детекторы пока не читают.
- Нарушения из блока «ЗАПЛАНИРОВАНО» (пересчёт без клиента или контролёра, проверка инкассаторской сумки и т. п.) не распознаются.
- Финальное видео жюри снято под другим углом. Зоны определяются по содержимому кадра, а не по фиксированным координатам, но качество на другом ракурсе не измерено.

Известные ошибки:

- R01 и R02 строятся от одного сигнала «кассира нет на рабочем месте» и могут сработать на одном интервале, если в кассе посетитель и на столе деньги или сумка.
- На части реальных видео сигналы «сейф открыт» и «личные вещи на столе» держатся с начала ролика: это даёт ложные R10 / R09 с таймкодом около 0 с. Пороги ещё настраиваются.
- R12 зависит от состояния «инкассаторская сумка», которое zero-shot распознаётся ненадёжно и по умолчанию выключено (`SceneConfig.enable_collection_bag = False` в `worker/scene/builder.py`). В текущей конфигурации R12 не срабатывает.
- R11 отличает постороннего от клиента по ситуации и месту: третий человек в комнате или вошедший, который встаёт на стороне кассира. Сторона определяется по оси «центр стола → рабочее место кассира» и зависит от того, верно ли найдены стол и рабочее место. Вход засчитывается только через дверь с переходом в комнату; если дверь не найдена, входов нет и R11 / R14 не срабатывают.
- Стеклянные стены и дверь: люди за стеклом и отражения отсекаются по размеру и положению рамки; при ошибке возможны ложные R01 / R11.
- Ролики с неопределённым типом в разметке (X-1, X-2, Х-11, Х-13, Х-22, Х-24, Х-28, Х-32, Х-34, Х-44, Х-47) отдельным правилом не покрыты и находятся, только если совпадают с одним из правил выше.

## Требования

- Docker ≥ 24 с Compose v2 (`docker compose version`).
- Для GPU: NVIDIA-драйвер и [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html) (на Ubuntu/Debian ставится скриптом `bash scripts/setup_gpu_docker.sh`). Проверка:

  ```bash
  docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
  ```

- Видеокарта NVIDIA: проверено на 6 ГБ видеопамяти (пик 3,7 ГБ).
- Python ≥ 3.9 на хосте — только для скачивания весов (`scripts/download_models.py`, только стандартная библиотека).
- Свободное место на диске: веса моделей ≈ 1,5 ГБ (`models/`) плюс образы Docker (TODO: уточнить размер после сборки worker с torch).

## Запуск

### 1. Клонирование

```bash
git clone <URL> && cd CompVision
```

### 2. Настройка `.env`

```bash
cp .env.example .env
openssl rand -hex 32   # сгенерировать API_KEY и вписать в .env
```

| Переменная         | По умолчанию | Назначение |
|--------------------|--------------|------------|
| `API_KEY`          | — (обязательна) | Ключ для жюри. Передаётся в заголовке `X-API-Key`; запросы без верного ключа отклоняются. Его же nginx подставляет в запросы интерфейса. |
| `FRONTEND_PORT`    | `8080`       | Единственный порт, открытый наружу (UI и API). |
| `WORKER_DEVICE`    | `cuda`       | Устройство инференса: `cuda` или `cpu`. |
| `LOG_LEVEL`        | `info`       | Уровень логирования backend и worker. |
| `MAX_UPLOAD_MB`    | `200`        | Максимальный размер загружаемого видео. |
| `JOB_TIMEOUT_SEC`  | `300`        | Лимит обработки одной задачи с момента загрузки (ТЗ: 5 минут). |
| `FEEDBACK_ENABLED` | `0`          | Сбор отзывов проверяющего; при проверке жюри оставлять `0` (см. [Отзывы проверяющего](#отзывы-проверяющего)). |
| `WORKER_POLL_SEC`  | `1.0`        | Необязательно. Период опроса очереди worker'ом, секунд. |

`RULES_PATH` (worker, `/app/rules.yaml`), `STORAGE_DIR`, `DATABASE_URL`, `MODELS_DIR` задаются в `docker-compose.yml`, в `.env` их менять не нужно.

### 3. Скачивание весов моделей

```bash
python3 scripts/download_models.py          # один раз, нужен интернет
python3 scripts/download_models.py --list   # показать список моделей
python3 scripts/download_models.py --force  # перекачать заново
```

Веса сохраняются в `models/` (с `models/MANIFEST.json` — sha256 и размеры) и монтируются в контейнеры как `/models` только для чтения.

Это **единственный шаг, требующий интернета** (кроме сборки образов). Дальше сервис работает полностью офлайн: в контейнерах выставлены `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`, а backend и worker находятся в сети без выхода наружу. Это соответствует требованию переносимости во внутренний контур банка (ТЗ, раздел 7).

### 4. Сборка и запуск

```bash
docker compose build
docker compose up -d
docker compose ps              # статус контейнеров
docker compose logs -f worker  # логи обработки
```

**Вариант без GPU.** В `docker-compose.yml` закомментируйте блок `deploy` у сервиса `worker` и установите `WORKER_DEVICE=cpu` в `.env`. Обработка на CPU заметно медленнее, лимит 5 минут на видео может не выдерживаться.

### 5. Проверка здоровья

```bash
curl -s http://localhost:8080/health
```

nginx проксирует `/health` на backend. Ожидаемый ответ: `{"status":"ok"}`. Также `docker compose ps` должен показывать `backend` и `frontend` в состоянии `healthy`, а `worker` — `running` (у него нет HTTP-порта и healthcheck).

### 6. Проверка API

Адрес сервиса для жюри: **будет указан при сдаче**. Ниже — `http://localhost:8080`.

Загрузка видео (пример из ТЗ, раздел 10):

```bash
curl -X POST http://localhost:8080/api/v1/analyze \
     -H "X-API-Key: <ключ из .env>" -F "file=@video_017.mov"
```

Ответ (пример):

```json
{"job_id": "3f2a9c1e04b7", "status": "processing"}
```

Получение статуса и результата:

```bash
curl -H "X-API-Key: <ключ из .env>" http://localhost:8080/api/v1/jobs/3f2a9c1e04b7
```

Результат после завершения обработки (формат раздела 10 ТЗ, `shared/schemas.py`; пример, название акта и base64 сокращены):

```json
{
  "job_id": "3f2a9c1e04b7",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Сейф с наличными оставлен открытым",
      "timecode_sec": 5.0,
      "description": "С 5.0 с дверца сейфа открыта, кассир за рабочим столом; кассир не находится у сейфа. Это может нарушать п. 20 (часть вторая) документа «Правила осуществления кассовых операций … № 231».",
      "evidence_frames": [
        { "timestamp_sec": 5.0, "image_base64": "/9j/4AAQ..." }
      ],
      "rule": { "id": "R10_storage_left_open", "doc": "Правила осуществления кассовых операций … № 231", "url": "https://adilet.zan.kz/rus/docs/V1900019680", "clause": "п. 20 (часть вторая)" }
    }
  ]
}
```

| Поле              | Описание |
|-------------------|----------|
| `status`          | `processing` — задача в очереди или обрабатывается; `done` — результат готов; `failed` — ошибка обработки или таймаут. |
| `verdict`         | `no_violation` или `violation` (только при `done`). |
| `violations`      | Список нарушений (не больше 5, по времени); пустой, если нарушений нет. |
| `type`            | Тип нарушения — `title` правила из `rules.yaml`. |
| `timecode_sec`    | Начало нарушения в секундах от начала видео. |
| `description`     | Что видно на видео и какой пункт акта это может нарушать. |
| `evidence_frames` | 1–3 кадра-доказательства (JPEG, base64) с таймкодом. |
| `rule`            | Необязательное расширение раздела 10 ТЗ: `{id, doc, url, clause}` — нормативный источник из `rules.yaml`. Ссылка на норматив всегда дублируется текстом в `description`. |

Файлы задачи из `STORAGE_DIR/<job_id>/` (исходное видео `input.mov`, кадры `frames/<name>.jpg`) отдаются маршрутом `GET /api/v1/jobs/{job_id}/files/{filename}`:

```bash
curl -H "X-API-Key: <ключ из .env>" -O http://localhost:8080/api/v1/jobs/3f2a9c1e04b7/files/input.mov
```

Коды ошибок: без заголовка `X-API-Key` или с неверным ключом — `401`; видео больше `MAX_UPLOAD_MB` — `413`; файл не `.mov` / QuickTime — `415`; несуществующая задача — `404`. Тело ошибки — `{"detail": "..."}`.

```bash
docker compose down       # остановить; данные в volume сохраняются
docker compose down -v    # остановить и удалить volume с задачами
docker compose up -d --build   # пересобрать и перезапустить после изменения кода
```

### Локальный запуск без Docker (для разработки)

Из корня репозитория (нужны Python 3.11+, ffmpeg и зависимости из `backend/requirements.txt` и `worker/requirements.txt`):

```bash
mkdir -p storage data
export STORAGE_DIR=./storage DATABASE_URL=sqlite:///./data/app.db API_KEY=dev-local-key-0123456789 RULES_PATH=./rules.yaml MODELS_DIR=./models
PYTHONPATH=. python -m uvicorn --app-dir backend app.main:app --port 8000   # терминал 1
PYTHONPATH=. python -m worker.main                                          # терминал 2
```

### 8. Публичный URL для жюри

Наружу открыт только порт `FRONTEND_PORT`. Для HTTPS поставьте перед ним reverse-proxy (Caddy, nginx) или туннель. UI и API доступны по одному адресу: `https://<host>/` и `https://<host>/api/v1/...`. Жюри передаются адрес сервиса и значение `API_KEY`.

### 9. Веб-интерфейс

Откройте `http://localhost:8080/` и загрузите `.mov`. Вводить ключ не нужно: интерфейс ходит на `/ui-api`, а nginx подставляет `API_KEY` сам. В браузер и в сборку ключ не попадает.

Путь `/ui-api` работает без ключа для любого, кто видит адрес сервиса. Это осознанный выбор: по FAQ п. 27 авторизация в интерфейсе не требуется. Путь `/api` для жюри по-прежнему требует ключ.

Для `npm run dev` задайте ключ в окружении, dev-прокси Vite подставит его так же, как nginx: `API_KEY=<ключ> npm run dev`.

Моковый режим интерфейса (только для вёрстки без backend; на работу сервиса не влияет) включается параметром `?mock=1` в адресе или переменной `VITE_MOCK=1` при `npm run dev`. Сценарий задаёт имя файла: `clean` даёт «нарушение не обнаружено», `fail` — ошибку обработки, `offline` имитирует недоступный сервер.

```bash
cd frontend && npm ci && VITE_MOCK=1 npm run dev
```

#### Отзывы проверяющего

Отзыв проверяющего (кнопки «Подтвердить / Отклонить» в карточке нарушения) по умолчанию выключен: по разделу 10 ТЗ тестовые видео жюри нельзя использовать для обучения, поэтому при проверке backend их не принимает (`POST /api/v1/jobs/{job_id}/feedback` → `404`), а интерфейс кнопки не показывает. Сбор включается переменной `FEEDBACK_ENABLED=1` в `.env` и нужен только на собственном датасете команды — для разбора ошибок детекторов. Интерфейс узнаёт текущее значение через `GET /api/v1/config`, пересобирать frontend не нужно.

### 10. Оценка на датасете

Скрипт прогоняет тот же пайплайн (`worker.runner.analyze`) напрямую, без HTTP и базы, и сравнивает результат с `dataset/annotations.csv`. Он печатает TP, FN, FP, TN по вердикту на видео, долю эталонных таймкодов, попавших в ±3 с, и время обработки.

```bash
PYTHONPATH=. python scripts/evaluate.py --dataset dataset/ --tolerance 3 --json eval.json
```

Нужны ffmpeg, веса в `models/` и зависимости из `worker/requirements.txt`; устройство берётся из `WORKER_DEVICE`, каталог весов — из `MODELS_DIR` (для запуска с хоста: `MODELS_DIR=./models`).

## Устранение неполадок

**Worker не видит GPU.** Проверьте, что GPU доступен внутри контейнера:

```bash
docker compose exec worker nvidia-smi
```

Если команда не работает — установите NVIDIA Container Toolkit (`bash scripts/setup_gpu_docker.sh`) и перезапустите Docker (`sudo systemctl restart docker`). Проверьте, что блок `deploy` у `worker` в `docker-compose.yml` не закомментирован и `WORKER_DEVICE=cuda`.

**413 Request Entity Too Large при загрузке.** Увеличьте `client_max_body_size` в `frontend/nginx.conf.template` и `MAX_UPLOAD_MB` в `.env`, затем пересоберите frontend.

**Изменили `rules.yaml`, а результат прежний.** Правила читаются при старте worker: `docker compose restart worker`.

**Порт занят.** Измените `FRONTEND_PORT` в `.env` и перезапустите `docker compose up -d`.

**`API_KEY is required` при `docker compose up`.** Не заполнен `.env`: скопируйте `.env.example` в `.env` и задайте `API_KEY`.
